项目讲解

从澳门硕士期间的市场洞察,到面向港澳商家的 GEO 平台落地

1. 项目是什么

创业背景

创始人在澳门攻读硕士期间,观察到一个显著的市场机会:港澳地区大量商家(餐饮、零售、酒店、个人IP)的核心客源是大陆游客,而大陆游客正在快速从传统搜索引擎转向AI搜索(豆包、DeepSeek、Kimi、千问)获取消费推荐和旅行攻略。然而,港澳本地商家普遍缺乏针对大陆AI平台的内容优化能力,导致在AI推荐结果中严重缺位——大陆游客问"澳门必吃餐厅",AI 推荐的全是大众点评上的老店,本地新兴品牌完全没有存在感。

产品定义

AI提名官是一个面向港澳商家的 GEO(Generative Engine Optimization,生成式引擎优化)自动化平台。简单说,传统 SEO 是让你的网站在百度/Google 搜索结果里排名靠前;GEO 是让你的品牌在 AI 回答里被主动提到和推荐。

当大陆游客在豆包、DeepSeek、Kimi、千问里问"澳门性价比高的葡国餐厅"时,如果 AI 的回答里提到了你的餐厅,这就是 GEO 的效果。AI提名官做的事情就是帮港澳商家实现这个目标,覆盖从选词到监控的全流程。

目标市场

首发市场锁定澳門和香港。目标用户包括:港澳本地餐饮品牌、酒店民宿、零售商家、个人IP、旅游服务商。核心价值是让港澳商家出现在大陆游客的AI搜索推荐结果中,精准触达跨境消费客群。

2. 整体架构

技术选型遵循"能用云服务就不自建"的原则,把精力集中在业务逻辑上:

3. 核心业务流

整个产品围绕四步闭环设计:

  1. 创建项目 — 港澳商家填写品牌名、行业、核心卖点、竞品信息,一个项目对应一个 GEO 推广计划(如"澳门XX葡国餐厅")
  2. 生成关键词 — 调用 DeepSeek API,基于 plant 公式(前缀词+主词+后缀词)生成大陆游客可能搜索的目标词(如"澳门必吃葡国菜推荐"),按高中低优先级分层
  3. 生成文章 — 选关键词 + 选文章类型(排行榜/年度盘点/选购指南/深度分析/QA),AI 生成面向大陆内容平台的 GEO 优化文章
  4. 监控检测 — 对每个关键词,分别调用四家大陆AI平台的 API 提问,检查回答中是否推荐了该商家,记录引用排名和引用片段

工程规范

SDD 规范驱动开发,用文档约束代码质量

1. SDD 规范驱动

SDD(Spec-Driven Development)的核心理念:先写规范文档,再写代码。在这个项目里,动手写第一行业务代码之前,先完成了三份规范文档:

  • CLAUDE.md — 工程总纲,定义技术栈、目录结构、命名规则、NEVER 红线
  • conventions.md — 编码细则,约束组件设计、TypeScript 用法、样式规范、错误处理
  • api-rules.md — API 接口规则,统一响应格式、鉴权方式、参数校验

这三份文档在整个开发过程中持续生效,所有代码变更都要符合文档里的约束条件,不符合的不允许合入。

2. CLAUDE.md 约束

CLAUDE.md 是整个项目的工程宪法,包含以下板块:

  • 技术栈锁定 — Next.js 15 + Tailwind CSS 4 + TypeScript + Supabase
  • 目录结构规范 — 每个目录的职责边界
  • 命名规范 — 组件 PascalCase,工具 camelCase
  • 导出规范 — 全部 named export,page.tsx 除外
  • 业务术语表 — plant 公式、目标搜索词、主稿、平台版本等
  • Git 规范 — feat/fix/refactor 前缀,中文描述
  • NEVER 清单 — 10 条不可违反的红线
  • 压缩指令 — 上下文压缩时必须保留的信息

3. 编码规范

conventions.md 约束具体的编码行为:

组件设计

  • Mobile First,从移动端写起用 md: lg: 扩展
  • 一个组件只做一件事,超过 150 行考虑拆分
  • 所有交互元素必须有 hover / active / focus 视觉反馈

TypeScript

  • 接口用 interface,联合类型用 type
  • API 响应必须定义完整类型,不允许 as any

错误处理

  • API 调用必须处理 loading / success / error 三态
  • 用户操作失败给中文提示,不暴露技术细节
  • 表单提交防重复点击,提交中禁用按钮

4. API 接口规范

所有 API Route 遵循统一规则:

  • 必须验证用户身份(检查 Supabase session)
  • 请求参数做类型校验
  • 返回统一格式:{ success: boolean, data?: T, error?: string }
  • 敏感操作必须检查资源所有权
  • 不在响应中暴露内部错误堆栈

5. NEVER 清单

10 条工程红线,任何情况下都不允许违反:

  1. 不使用 any 类型,必须定义明确的类型
  2. 不在组件中直接调用 API,必须通过 hooks 或 lib 层
  3. 不硬编码颜色/字号/间距,必须使用 Tailwind design token
  4. 不提交 .env 文件或任何包含密钥的文件
  5. 不使用 git push --force
  6. 不删除非自己创建的文件,除非明确要求
  7. 不一次性重构超过 3 个文件,大重构必须分步
  8. 不在前端暴露 Supabase service_role key,只用 anon key
  9. 不跳过手机验证码校验逻辑
  10. 不在文章生成中使用极限词(最、第一、100%、顶级)

6. Harness 质量体系

Harness 是保障代码质量的验证体系,在这个项目里体现在三个层面:

编译期验证

  • TypeScript 严格模式,每次变更前 npx tsc --noEmit 零错误才允许提交
  • 全量代码零 any,类型系统覆盖所有数据结构

运行时防护

  • API 层统一错误捕获,try-catch 包裹所有外部调用
  • 前端三态覆盖(loading/success/error/empty),用户永远能看到明确的状态
  • AI API 调用的超时和错误隔离,单个平台失败不影响其他

安全边界

  • RLS 行级安全策略,数据库层面隔离用户数据
  • API Route 强制鉴权,未登录直接返回 401
  • .env.local + .gitignore 保护密钥不泄露

Prompt Engineering

3 套核心 Prompt 的设计思路与约束规则

1. PE 设计思路

这个项目有 3 个需要 Prompt 的场景,设计原则一致:

  • 结构化输出 — 所有 Prompt 都要求 AI 返回 JSON 格式,方便程序解析
  • 角色设定明确 — system prompt 锁定身份(GEO 专家 / 普通用户),防止角色漂移
  • 约束条件前置 — 不要什么(极限词、贬低竞品)写在要什么前面,优先级更高
  • 上下文注入 — 把港澳商家信息(品牌名、行业、卖点、所在地区)作为变量注入,让输出精准匹配大陆游客搜索场景

2. 关键词生成 Prompt

基于 plant 公式(前缀词 + 主词 + 后缀词 = 目标搜索词)生成关键词矩阵。

设计要点
  • 一次生成 12 组,按 3 档优先级分层(高 4 + 中 4 + 低 4)
  • 注入项目的 target_name、industry、competitors 作为上下文
  • 要求主词从核心品类逐步外扩到细分赛道
  • 后缀词决定 AI 回答形式:推荐/排行榜/怎么选/测评
  • 输出格式:JSON 数组,每个元素含 prefix/main_word/suffix/full_keyword/priority

3. 文章生成 Prompt

支持 5 种文章类型,每种对应不同的 AI 回答场景:

类型场景触发搜索词后缀
排行榜型游客搜"澳门葡国餐厅排行榜"时被引用排行榜、推荐、哪家好
年度盘点型游客搜"2026年香港必去景点"时被引用2026年、最新、盘点
选购指南型游客搜"澳门伴手礼怎么选"时被引用怎么选、如何挑、攻略
深度分析型游客搜"澳门酒店对比分析"时被引用分析、对比、测评
QA问答型游客搜"香港XX店怎么样"时被引用怎么样、好不好、值得吗

8 条写作约束:

  1. 标题必须包含目标关键词
  2. 文章 1500-2500 字,结构清晰有小标题
  3. 必须包含具体数据(数字、百分比、年份)
  4. 品牌名自然出现 2-3 次,不堆砌
  5. 禁止极限词("最好""第一""100%")
  6. 提到竞品时客观对比,不贬低
  7. 文章要有权威感,像行业专家写的
  8. 包含可被 AI 引用的结论性语句

4. 监控检测 Prompt

检测 Prompt 的设计目标:模拟大陆游客在 AI 搜索引擎里搜索港澳消费推荐的真实行为,拿到 AI 的自然回答,再分析回答里有没有提到商家品牌。

System Prompt

"你是一个普通用户在使用AI搜索引擎。请根据用户的问题给出详细、客观的回答。回答中如果涉及品牌/产品推荐,请列出你认为值得推荐的,并简要说明理由。"

回答分析逻辑(代码实现,非 Prompt):

  • 品牌判定 — 检查回答文本中是否包含 target_name(不区分大小写)
  • 排名估算 — 如果回答是编号列表,找品牌在第几条;否则按段落位置估算
  • 片段提取 — 截取品牌名前后各 50-100 字作为引用片段

5. 约束与防护

Prompt 层面的安全约束:

  • system prompt 用"只返回 JSON 对象,不要返回其他内容"锁定输出格式,防止 AI 加额外解释
  • temperature 设置:写稿用 0.7(保持创意),检测用 0.3(追求稳定)
  • 极限词过滤写在 Prompt 约束里,从生成源头拦截
  • 代码层面用 result.match(/\{[\s\S]*\}/) 提取 JSON,容错 AI 返回多余文本

Vibe Coding 复盘

以 PE / SDD / Harness 三维度复盘 Vibe Coding 全过程

1. 什么是 Vibe Coding

Vibe Coding 是指通过自然语言指导 AI 编程助手完成产品开发的工作方式。开发者的核心职责从"写代码"转变为"定义需求、设计架构、约束质量"。

评价一个 Vibe Coding 项目的质量,主要看三个维度:

  • PE(Prompt Engineering) — 你给 AI 的指令质量如何,能不能让 AI 产出可控、稳定的结果
  • SDD(Spec-Driven Development) — 你有没有在写代码前定义好规范,用文档驱动开发
  • Harness — 你有没有搭建验证体系,在 AI 产出代码后能自动检查质量

2. PE 维度自评

做得好的

  • CLAUDE.md 作为全局 system prompt,给 AI 助手定义了完整的项目上下文、约束条件和术语表
  • 业务 Prompt(关键词/文章/检测)都做了结构化输出约束,JSON 格式统一且稳定
  • 用 NEVER 清单明确禁区,防止 AI 越界(比如用极限词、暴露 service_role key)

可以改进的

  • 关键词生成 Prompt 缺少 few-shot 示例,AI 有时候对 plant 公式理解不够精准
  • 没有做 Prompt 版本管理,迭代过程中的中间版本没有保留

3. SDD 维度自评

做得好的

  • 动手写代码前先完成了三份规范文档(CLAUDE.md / conventions.md / api-rules.md),开发全程有据可依
  • 数据库 6 张表的字段、类型、关联关系在建表 SQL 里一次性定义清楚,后续没有反复改表
  • types/database.ts 集中定义所有类型,前后端共享,改一处全局生效

可以改进的

  • 缺少 PRD 或用户故事文档,需求是口头沟通后直接开发,没有书面留痕
  • API 接口没有写 OpenAPI/Swagger 文档,接口契约只存在于代码里

4. Harness 维度自评

做得好的

  • TypeScript 严格模式 + 零 any,每次提交前跑 tsc --noEmit,编译不过不提交
  • API 层统一 try-catch + 统一响应格式,任何一个外部调用失败都有兜底
  • 前端所有面板覆盖 loading / success / error / empty 四态,用户不会看到白屏或卡死
  • 监控检测做了错误隔离 — 一个平台超时不影响其他三个平台的结果

可以改进的

  • 没有写单元测试和集成测试,质量验证完全靠类型系统和手动测试
  • 没有接入 CI/CD 流水线的自动化检查,lint 和 type check 靠手动执行
  • 缺少端到端测试,关键业务流没有自动化回归保障

5. 踩坑与经验

千问 API 兼容性

千问的 OpenAI 兼容模式不接受 max_tokens 参数,发了直接返回 400。其他三家都正常。解决方案:对千问跳过该参数。教训:号称"兼容"不等于"完全一致",每家都要实际测一遍。

Vercel Serverless 超时

Hobby 计划函数超时 10 秒。最初把 12 个关键词 x 4 个平台的检测放在一个 API 调用里,48 次 AI 调用总耗时远超 10 秒。解决方案:前端逐个关键词、逐个平台发起请求,每次请求只调一家 API,控制在 10 秒内。

Vercel 部署缓存

git push 后 Vercel 自动部署,但如果在部署过程中手动 Redeploy,会基于旧的 commit 重新构建,导致最新代码没上线。解决方案:空 commit 触发新的自动部署,或等 Redeploy 完成后再 push。

Twilio 短信地区适配

Twilio 无法向中国大陆手机号(+86)发送短信(中国运营商拦截境外短信)。这反而验证了产品定位的正确性——目标市场就是港澳,港澳手机号(+853/+852)通过 Twilio 发送验证码完全正常。最终方案:登录页只保留港澳区号,Supabase Phone Auth + Twilio 对接港澳短信通道。
